  How to animate it

  The idea: at any playback time T, draw every stroke that finished before T,
  plus the current stroke up to T.

  1. Data model. All the preparation happens once, when the file is loaded:
  - InkPoint(Offset pos, double t): positions converted to mm and times shifted
    to start at 0.
  - Stroke(List<InkPoint> points, Path path, double tStart, double tEnd).
  - Note(List<Stroke> strokes, Rect bounds, double duration).
  - The parser is simple: skip the header row and use double.parse, which
    already understands values like -7.1898e-05.

  2. Fitting the note to the screen. Scale by min(canvasW / bounds.width, 
  canvasH / bounds.height), add some padding, and move the note so
  bounds.topLeft sits at the origin. Keep the data in mm and only scale when
  painting, so it works at any screen size.

  3. Timeline. An AnimationController (or Ticker) produces the playback time T.
  On top of that:
  - A speed setting (0.5×, 1×, 2×).
  - An option to shorten pauses (for example, cap them at 0.25 s) so long
    hesitations don't stall the replay. Work this out once by building a new
    time for each point.
  - Scrubbing with a slider is free, because the drawing depends only on T.

  4. Drawing a frame (CustomPainter with repaint: controller):
  for (final s in note.strokes) {
    if (s.tEnd <= t) { canvas.drawPath(s.path, ink); continue; } // finished 
  stroke
    if (s.tStart > t) break;                                     // not started 
  yet
    final i = lowerBound(s.points, t);   // binary search for the last point 
  before t
    // draw points 0..i, plus a point between i and i+1 matching t exactly,
    // so the stroke grows smoothly between samples
  }
  - Paint settings: StrokeCap.round, StrokeJoin.round and PaintingStyle.stroke.
    Round ends make the short dot strokes show up.
  - Optionally draw a small pen tip at the current point. It makes the replay
    feel live.

  5. Performance. These notes are small: under 4,000 points. Building each
  stroke's Path once and redrawing it every frame is fine. For longer notes,
  record the finished strokes into a ui.Picture and add to it only when a stroke
  completes. You could also simplify each stroke (Ramer–Douglas–Peucker at
  about 0.03 mm) to keep 5–10× fewer points, keeping each remaining point's
  timestamp.

  6. Optional extras:
  - Line thickness from speed, using the speed between neighbouring points
    smoothed out, as a stand-in for pressure.
  - Straightening note_3.
  - A "stroke by stroke" mode that ignores real timing.
  - Exporting to video or GIF later by sampling T at a fixed frame rate.

⏺ I've written the architecture plan to Doc/ARCHITECTURE_PLAN.md. It's a plan
  only: no app code exists yet, so none of it has been tested.

  MVVM
  - Layers: a CSV parser and a note store (repository) at the bottom, then
    ViewModels, then the screens.
  - No extra packages: ViewModels use Flutter's built-in ChangeNotifier and
    ValueNotifier, and dependencies are passed in through constructors.
  - Folder layout: the plan includes a full one for lib/, following Flutter's
    official architecture guide.

  Smooth 60–120 fps
  - A Ticker drives playback, firing once per screen refresh at whatever rate
    the display runs.
  - iPhones also need the CADisableMinimumFrameDurationOnPhone setting, or they
    stay at 60 Hz.

  Timestamp accuracy
  - Each frame works out the playback time from the frame's timestamp and the
    last play/seek point. It never adds up time steps, so there's no drift and
    the frame rate doesn't matter.
  - The pen tip is placed at the exact playback time, between two recorded
    points, so the drawn ink always matches the recording at that moment.
  - If a frame is dropped, the next one draws all the points it missed, so no
    ink is skipped.

  Only the canvas repaints
  - The canvas has two layers, each in its own RepaintBoundary:
    - Finished strokes: redrawn only when a stroke completes, about 8–24 times
      per replay.
    - Current stroke: redrawn every frame, but it draws only that one stroke.
  - The ViewModel uses a separate signal for each update rate. The per-frame
    signal reaches only the painters, so it triggers repaints but never
    rebuilds.
  - The progress bar is a painted widget rather than a Slider, so it doesn't
    rebuild every frame.

  Nothing heavy per frame
  - Storage: points are kept in flat typed lists (Float32List/Float64List) that
    are passed straight to drawRawPoints, with no copying and no Path objects.
  - Scaling: the fit-to-screen scale is applied once per frame on the canvas,
    not to every point.
  - Point lookup: a cursor moves forward through the points each frame, so there
    are no full scans. Binary search runs only when you seek.

  Things to know
  - Exception to "only the canvas": the time label rebuilds at most 10 times a
    second. You can switch it off.
  - Ink must be fully opaque. The fast drawing method darkens translucent ink
    where segments overlap.

  The plan also covers edge cases, a testing strategy and 7 build steps. One
  test checks that the screen rebuilds zero times during playback.

  When you'd need something more

  These cases are beyond what these 5 notes need, but worth knowing:
  - Much bigger notes (full pages with 100k+ points). Redrawing all finished
    strokes each time one completes gets expensive. The fix is to draw only the
    new stroke on top of a cached image (ui.Image), or to split finished ink
    into several layers each wrapped in RepaintBoundary.

    width, so you'd switch to Canvas.drawVertices, using a triangle mesh built
    once per stroke.

  A correction to the plan. Doc/ARCHITECTURE_PLAN.md (§5.2) says the
  finished-strokes layer is "reused unchanged by the compositor" and gives "the
  benefit of caching". That's only half true. RepaintBoundary saves the CPU from
  re-recording the drawing commands. But Impeller, Flutter's default renderer
  on iOS and Android, doesn't keep Skia's raster cache, so the GPU still draws
  all of those commands again every frame. For 4,000 points that doesn't matter.
  For millions it means the GPU works harder every frame as the replay goes on,
  which is exactly the growing GPU usage you asked about.

  The three changes

  1. Bake finished ink into images. When a stroke finishes, draw the previous
  image plus that one stroke into a new image with Picture.toImageSync. Each
  commit then costs one stroke, not all of them. Each frame, the GPU draws a few
  images plus the active stroke, which is constant work. To keep memory bounded
  on large notes, use tiles (for example 512×512 px squares, each its own
  image):
  - A finished stroke updates only the tiles it touches.
  - Tiles that scroll off screen are freed (least-recently-used first) and
    redrawn from the stroke data when they come back.
  - Each tile is about 1 MB, so a phone screen needs about 20–30 MB of tiles,
    whatever the note's size.

  2. Draw only what's visible. Store a bounding box for each stroke, computed at
  load time, and draw only tiles and strokes inside the visible area. Since
  writing mostly goes line by line, a per-line or per-tile index of strokes
  makes this lookup cheap. GPU cost then depends on the screen, not the note.

  3. Add a camera. Show the note at a readable zoom, follow the pen as it
  writes, and let the user scroll and zoom. When the zoom changes, the tiles are
  redrawn at the new scale, showing the old tiles scaled up or down until the
  new ones are ready.

  Data loading for this size:
  - Parse in a background isolate in chunks, not as one string.
  - Convert the CSV once into a binary format.
  - Optionally simplify the strokes, which keeps 5–10× fewer points with their
    timestamps unchanged.
  - Store times as Float32 offsets from each stroke's start, which halves the
    memory used for time.

  The finished-strokes repaint costs roughly tens of milliseconds near the end
  of a long note, against a frame budget of 8.3 ms at 120 Hz or 16.7 ms at 60
  Hz. At normal speed a stroke finishes every 0.3–0.5 s, so you'd see a stutter
  several times a second, more often at 2–4× speed. Each repaint also builds a
  new ~30 MB copy of the drawing commands and frees the old one, which churns
  memory.

  Raster thread: the biggest cost

  This adds to my previous answer, where I described this as GPU cost. Much of
  it is actually CPU cost.

  - Every frame, the raster thread replays all the layers' drawing commands,
    including the finished-strokes layer that the UI thread didn't touch.
  - As I understand Impeller, it converts each round-capped line segment into
    triangles on the CPU before uploading them to the GPU. It doesn't keep those
    triangles between frames.
  - So the cost every frame is proportional to all finished ink, even when
    nothing new was drawn.
  - At a rough 50–100 ns per segment, 3.8 million segments take hundreds of 
    milliseconds per frame. Near the end of the note, playback would drop to
    single-digit fps.
  - By the same rough maths, an 8.3 ms frame budget fits about 80k–160k
    segments. That's only about 20–40 written lines before 120 Hz playback
    starts dropping frames, much less than thousands.
  - Sustained raster-thread load also heats the phone. The phone then slows
    itself down (thermal throttling), which makes the frame drops worse.

  Part 2: A live stream at 411 Hz

  The same rule applies: the screen shows whatever has arrived by the time each
  frame is drawn. A live stream needs a few extra pieces, though, because
  samples arrive unevenly and drawing must stay decoupled from the stream's
  rate.

  1. Receive data in batches, not one event per sample. 411 Dart stream events a
  second, each with its own object, is wasteful. Bluetooth (BLE) delivers data
  in packets roughly every 7.5–30 ms anyway. So have the native side send one 
  typed-list batch per packet, 2–12 samples packed into a Float32List, through
  an EventChannel. That's about 30–130 messages a second and about 8 KB/s, which
  the main thread handles easily. If decoding the raw pen data turns out to be
  expensive, move it to a background isolate.

  2. Store samples in a buffer that only grows. Append each batch to typed-list
  chunks rather than one growing list, so nothing is ever copied when it grows.
  Add to the stroke table on pen-down and pen-up. The existing cursor works as
  is: it reads up to the newest sample.

  3. Never repaint from the stream. Incoming data only appends to the buffer and
  sets a "new data" flag. Repainting stays tied to the frame clock. Many
  batches between two frames cause one repaint; no new data causes no repaint.
  Calling notifyListeners for every packet would do work that's thrown away.

  4. Pick one of two live display modes:

  Mode: As fast as possible
  What's drawn each frame: Everything received so far
  Delay: Bluetooth delay + up to one frame
  Look: Ink grows in small bursts, one per packet
  ────────────────────────────────────────
  Mode: True-speed (recommended)
  What's drawn each frame: Ink up to the newest pen time minus a small buffer
  (for example 40 ms)
  Delay: +40 ms
  Look: Ink grows smoothly at the real pen speed, like the CSV replay

  True-speed mode works like video streaming: it holds back a little data to
  hide uneven arrival. It also needs to match the pen's clock to the phone's
  clock. Track the smallest difference between "arrival time" and "pen time"
  over a sliding window, which also corrects slow drift between the two clocks.
  Because the clock is shared, the same ActiveInkPainter and cursor serve both
  CSV and live playback.

  5. Detect lost packets. BLE notifications aren't acknowledged, so packets can
  be lost when a buffer overflows. The pen's clock never stops (my previous
  answer), so each sample's expected index is (t − t₀) / 2.4327 ms. A jump in
  that index inside a stroke means samples were lost. Then you can mark the gap,
  draw a straight line across it, or ask the pen to resend if its protocol
  supports that.

  6. Use whole-number timestamps. Ask for a sample counter or integer
  microseconds rather than seconds as a float. That avoids the CSV's rounding
  problem completely.

  7. Long sessions need the tile approach from before, because finished ink
  keeps growing forever.

  Effect on the architecture:
  - Add an InkSource interface in the data layer, with two versions:
    - CsvInkSource: everything at once, with a known end.
    - LiveInkSource: a stream of batches with no known end.
  - Both feed the same append-only InkBuffer.
  - The replay ViewModel, cursor, clock and painters stay the same. The only
    differences are that the end time keeps growing and seeking is limited to
    data already received.

⏺ I've added the search bar to the Home screen plan in Doc/SCREENS_PLAN.md. This
  changes the plan only; no screen code exists yet.

  How it works:
  - Placement: a Material 3 SearchBar sits directly under the "Notes" title and
    is always visible, with the hint "Search notes" and a clear (✕) button that
    appears once you type.
  - What it searches: the title only, since that's the only text a note has.
    Searching the handwritten words would need handwriting recognition.
  - Matching: upper or lower case doesn't matter, and it matches anywhere in the
    title, so "3" finds "Note 3" and "note" finds all five. The list updates as
    you type, with no search button.
  - No matches: the list is replaced by "No notes match "…"" with a Clear search
    button. That's separate from the "No notes yet" state, which means there
    are no notes at all.
  - Other states: the search bar is shown but disabled while loading, when there
    are no notes, and on error.
  - Keeping the search: it stays when you open a note and come back, and resets
    when the app restarts.

  Where it lives in MVVM:
  - The ViewModel holds the search text and the filtered list, with search() and
    clearSearch() commands. Filtering happens there, not while the screen
    builds.
  - The screen only owns the text field's controller and passes each change to
    the ViewModel.

  Also updated:
  - Layout sketch: now shows the search bar under the title.
  - Accessibility: the field and its clear button get labels, and screen readers
    announce how many notes match as you type.
  - Tests: cases for the matching rules, the no-match message and keeping the
    search after visiting a note.
  - Build order: steps 3–4 now include the search work.

  The detail screen section is still waiting for its requirements.

  Main design points:
  - Showing the complete note and replaying it use the same canvas. The complete
    note is just a replay paused at the end, so the two can never look
    different. Once paused, it uses no CPU or GPU.
  - The canvas has three layers. I'm adding a paper layer under the two ink
    layers from the architecture plan. Paper redraws only on resize or a setting
    change. Ink colour changes redraw the ink once.
  - The dot grid has a dot every 5 mm, lined up with the ink so it scales with
    the note. The dot positions are worked out once, not every frame.
  - The pen tip is a dot at the exact pen position. It shows while the pen is
    down, including when paused mid-stroke, and is hidden between strokes and on
    the complete note.
  - The settings sheet has three sections:
    - ink colour swatches, with a check mark on the selected one,
    - a Blank / Dot grid toggle,
    - the Show Pen Tip Indicator switch.

    Changes apply immediately, and playback keeps running so you can see the
    effect.
  - Settings storage: a new CanvasSettingsRepository holds them in memory. It
    can be swapped for one that saves to the device later without changing the
    screen.
  - Ink colours: all five are fully opaque, as the architecture plan requires. I
    checked their contrast against the paper: 5.0:1 to 17:1, above WCAG's 3:1
    minimum for graphics.

  One change to existing code: Home will pass the whole note summary to the
  detail screen instead of just its id. That way the title shows straight away,
  while the CSV is still loading.

  The plan also covers screen states, accessibility, the files involved (4 of
  them new), the tests and a 7-step build order. The tests include one that
  checks the screen rebuilds 0 times during playback.

  I also noticed app.dart now sets darkTheme: AppTheme.light, which makes the
  app light-only. I've assumed that's intentional and picked the paper and ink
  colours for a light background. If you meant to keep dark mode, the canvas
  colours will need dark versions.

⏺ I've built the new-note feature. flutter analyze reports no issues, but the 
  app hasn't run on a device and none of the tests have run: the plugin hook
  still blocks flutter test. Handwriting input especially needs a try on a real
  phone or tablet.

  How it works:
  1. Home has a floating + button (tooltip "New note"). It shows in every state,
     even if the note list fails to load, and the list leaves space underneath
     so it never covers the last note.
  2. New note screen: a fresh canvas with your current paper and ink colour, and
     a "Write anything" hint. You write with a finger, stylus or mouse.
     - Undo and Clear are in the app bar.
     - An Animate button appears once you've finished a stroke.
     - Going back with ink on the canvas asks "Discard this note?" first.
     - Only the first finger or pen draws until it lifts, so a resting palm
       doesn't add strokes.
  3. Animate adds the note to Home as "New note 1", "New note 2" and so on, and
     opens the replay, which starts playing straight away. Back from the replay
     returns to Home, where the new note is already listed, with no loading
     spinner and your search kept.

  The new note replays at the timing you actually wrote it. Pen writing in the
  stats shows your device's touch sampling interval, for example 8.33 ms at 120
  Hz, instead of the pen's 2.43 ms.

  Choices I made that you may want to change:
  - New notes are kept in memory only. They disappear when the app restarts.
    Saving them is a separate piece of work.
  - The replay auto-plays for new notes only. Notes opened from the list still
    open on the complete note.
  - A zoom cap on replay. Replay now zooms in at most 20 px/mm, so a single
    scribbled word isn't blown up to fill the screen. This also applies to the
    CSV notes, but none of them gets near the cap.

  How it fits the architecture:
  - Recording: strokes are recorded into growable typed buffers, with no object
    per point, then turned into the same Note model the CSV notes use. So the
    replay engine, settings and stats work unchanged.
  - New code:
    - InkRecording (domain)
    - DrawNoteViewModel
    - DrawNoteScreen and its two painters, in lib/ui/draw/
  - No rebuilds while writing: pointer moves repaint only the live-ink layer.
    Widgets rebuild only when a stroke ends, on undo, or on clear.
  - Changes to existing code:
    - NoteSummary.assetPath is now optional, since drawn notes have no CSV.
    - The repository gains addDrawnNote.
    - The Home ViewModel gains refresh().
    - The replay screen gains autoPlay.

  Tests: about 30 new cases. They cover the recording model, the writing
  ViewModel and screen, plus additions to the repository, Home and replay tests.
  The screen tests draw strokes with timestamps and check Animate, Undo and the
  discard prompt. They also check that Back from the replay lands on Home.

  Docs: the design is in the new Doc/NEW_NOTE_PLAN.md. The Home plan gains
  requirement H6, which points to it.
